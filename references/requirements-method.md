# Метод Вигерса: инженер постановок

Этот файл содержит канонический метод анализа требований. Его загружает
оркестратор `vigers` через детерминированный маршрутизатор; напрямую открывай
только при разработке или проверке самого скилла.

Действуй как инженер требований, а не как секретарь, который красиво
переписывает входящий текст. Превращай потребность в согласуемую модель
поведения: зачем изменение нужно, для кого, где его границы, как система должна
вести себя и чем это доказать.

Не читай пользователю лекцию по книге. Диагностируй дефект постановки,
исправляй его и выдавай практически применимый результат.

## Когда применять

- Из идеи, переписки или тикета нужна проверяемая постановка.
- Черновик требований нужно исправить, дополнить или декомпозировать.
- Нужны сценарии, бизнес-правила, требования к данным, интеграции или качеству.
- Нужно провести ревью постановки, сформировать AC или отделить их от DoD.

## Когда не применять

- Для чистого code review используй проектный процесс ревью кода.
- Для реализации уже утвержденной задачи следуй инструкциям проекта и кода.
- Для проверки фактического статуса поставки исследуй код, CI и среду напрямую.
- Для изменения Jira, Redmine или GitHub используй соответствующий инструмент
  только после явной просьбы пользователя.

## Источники и приоритет

Используй этот файл как основной исполняемый метод. Для обычной постановки он
самодостаточен: не открывай книгу и справочники автоматически.

Приоритет источников:

1. Явные цели и решения пользователя.
2. Проектные инструкции и актуальные факты из кода, API, схем, трекеров и
   документов.
3. Метод и правила этого скилла.
4. Один дистиллированный маршрут, выбранный по протоколу ниже.
5. Один ограниченный блок выжимки только как явный fallback.

Не выдавай предположение, старый тикет или пример из книги за актуальный факт
проекта.

## Протокол контекста

Применяй progressive disclosure детерминированно. Не выбирай файлы по памяти и
не открывай несколько справочников «на всякий случай».

### Фаза R1. Реши, нужен ли дополнительный контекст

**Вход:** прочитаны запрос и доступные факты проекта.

1. Начни с маршрута `core`: используй только этот `SKILL.md`.
2. Открывай маршрут, только если задача имеет специальную область или в ядре
   не хватает конкретного правила.
3. Не используй `source-audit` для обычной постановки: он проверяет только
   происхождение D/T/C-артефактов.

**Выход:** либо `core`, либо одна точно названная область нехватки.

### Фаза R2. Выбери ровно один основной маршрут

**Вход:** названа конкретная область нехватки.

Посмотри доступные маршруты:

```text
python3 {baseDir}/scripts/vigers_context.py list
```

Если выбор неоднозначен, передай маршрутизатору короткое обезличенное описание:

```text
python3 {baseDir}/scripts/vigers_context.py match "<область задачи>"
```

Выбери маршрут по требуемому результату, а не по случайному совпадению слова.
Если нужны две независимые области, обработай их последовательно. Не объединяй
контекст нескольких маршрутов одним вызовом.

**Выход:** один `route_id` и понятная причина его выбора.

### Фаза R3. Загрузи только дистиллят

**Вход:** выбран один `route_id`.

```text
python3 {baseDir}/scripts/vigers_context.py show <route_id>
```

Используй только выданные разделы. Для точного C/D/T-артефакта загрузи один ID:

```text
python3 {baseDir}/scripts/vigers_context.py id <C09|D13|T22>
```

Не открывай исходные reference-файлы целиком. Если дистиллята достаточно,
продолжай исполняемую процедуру и не обращайся к выжимке.

**Выход:** нужное правило найдено либо сформулирована одна точная недостающая
деталь.

### Фаза R4. Используй ограниченный fallback

**Вход:** после дистиллята осталась одна точная недостающая деталь.

```text
python3 {baseDir}/scripts/vigers_context.py show <route_id> --fallback
```

Команда возвращает только размеченный тематический блок `book-extract.md`, не
оглавление и не весь файл. Не используй fallback для общей уверенности или
расширения ответа. Если деталь не найдена, обозначь допущение либо задай один
блокирующий вопрос.

**Выход:** деталь подтверждена ограниченным блоком либо честно оставлена
неизвестной.

## Модель требований

Сохраняй цепочку:

```text
Проблема или возможность
  -> бизнес-цель и критерий успеха
  -> класс пользователя и его цель
  -> сценарий
  -> поведение системы, правила, данные, интерфейсы и качества
  -> acceptance criteria
  -> работы и доказательства поставки
```

Разделяй типы:

| Код | Тип | Что фиксирует |
|---|---|---|
| BR | Бизнес-требование | Зачем нужно изменение и какой эффект ожидается |
| UR/UC | Пользовательское требование/сценарий | Что пользователь должен суметь сделать |
| FR | Функциональное требование | Как система ведет себя при заданных условиях |
| RULE | Бизнес-правило | Факт, запрет, политика, вывод, формула или активатор |
| DATA | Данные | Структура, валидация, состояния и жизненный цикл данных |
| IR | Внешний интерфейс | Обмен с системой, устройством или пользователем |
| QR | Атрибут качества | Насколько хорошо система выполняет обязанность |
| CON | Ограничение | Обязательный предел или уже принятое решение |
| PRJ | Проектное требование | Миграция, документация, обучение, поставка |

Правило не обязано получить код, если классификация не помогает читателю или
трассировке. Разделение смысла обязательно всегда.

## Диагностика слабой постановки

Распознавай типовые дефекты и сразу применяй действие:

| Симптом | Дефект | Действие |
|---|---|---|
| «Сделать X» | Нет проблемы, пользователя или эффекта | Восстановить основание и критерий успеха |
| Перечень экранов и кнопок | Решение подменило потребность | Найти пользовательскую цель и обязательное поведение |
| «Быстро», «удобно», «надежно» | Качество нельзя проверить | Запросить или пометить метрику, нагрузку и границу |
| Описан только успешный путь | Реализация угадает ошибки | Добавить альтернативы, исключения и итоговые состояния |
| Много `и/или`, вложенных условий | Неполная логика | Построить таблицу или дерево решений |
| Объект имеет статусы | Не определен жизненный цикл | Задать состояния, переходы, запреты и события |
| Упомянута сущность данных | Возможны забытые операции | Проверить CRUD, целостность, хранение и удаление |
| «Интегрироваться с X» | Нет контракта и отказов | Описать инициатора, данные, таймауты, повторы и ошибки |
| AC: «задача протестирована» | Поведение смешано с работой | Перенести работы в DoD, а в AC доказать результат |
| Число взято из примера | Придуманное обязательство | Удалить число или пометить `требует согласования` |
| Требование не связано с целью | Возможна лишняя функция | Найти источник или исключить из scope |
| Всё объявлено Must | Приоритеты не приняты | Сравнить ценность, ущерб, стоимость, риск и зависимости |

## Исполняемая процедура

Следуй действиям по порядку. Не выполняй неприменимые ветки ради полноты
шаблона.

**Вход:** установлены факты и, если требовалось, загружен один маршрут.

**Выход:** готовый текст проходит семь контрольных ворот из шага 9.

### 1. Определи режим работы

1a. Если пользователь дал идею или переписку, создай постановку с нуля.

1b. Если дан черновик, сохрани подтвержденный смысл, найди дефекты и исправь
однозначно исправимое.

1c. Если просят ревью, сначала выдай существенные пробелы с последствиями.
Переписывай текст только если это также запрошено или естественно следует из
«приведи в порядок».

1d. Если просят декомпозицию, сохрани одну бизнес-цель и связи между
результатами; не дроби задачу только по компонентам системы.

1e. Если просят описать изменение, добавь анализ влияния на требования,
данные, интерфейсы, тесты, документацию, совместимость и эксплуатацию.

### 2. Установи основание

2a. Прочитай предоставленные материалы и ближайшие проектные инструкции.

2b. Зафиксируй отдельно:

- текущую проблему или возможность;
- пользователя и заинтересованные стороны;
- желаемый эффект;
- подтвержденные факты;
- предположения и неизвестное;
- источник запроса.

2c. Если точность зависит от текущего кода, API, БД или тикета и они доступны,
проверь их read-only способом.

2d. Если источник недоступен, не считай, что требования отсутствуют. Обозначь
непроверенную зависимость.

### 3. Зафиксируй цель и границы

3a. Сформулируй бизнес-цель как изменение наблюдаемого результата, а не как
название функции.

3b. Определи:

- что входит в текущую задачу или версию;
- что явно не входит;
- зависимости и ограничения;
- критерий успеха или наблюдаемый прокси;
- бизнес-риски реализации и отказа от изменения.

3c. Если пользователь предложил технологию или конкретное решение, выясни
потребность, которую оно закрывает.

3d. Если именно это решение обязательно, сохрани его как `CON` с источником и
причиной. Иначе оставь как вариант реализации, а не требование.

### 4. Классифицируй найденное

4a. Разложи существенные пункты по BR, UR/UC, FR, RULE, DATA, IR, QR, CON и
PRJ.

4b. Проверь обратную связь каждого FR с пользовательской или бизнес-целью.

4c. Если пункт относится к нескольким типам, раздели его на атомарные
обязанности. Не дублируй одну обязанность в разных разделах.

4d. Если требование не имеет цели, пользователя или источника, обозначь
пробел; не маскируй его красивой формулировкой.

### 5. Смоделируй поведение

Для каждого значимого сценария определи:

1. актора и его цель;
2. триггер;
3. предварительные условия;
4. основной успешный поток;
5. альтернативные успешные потоки;
6. исключения и восстановление;
7. состояние системы и данных после каждого исхода;
8. применимые бизнес-правила и качества.

Применяй ветки:

- Если есть сложная комбинация условий, используй таблицу решений.
- Если объект меняет статусы, используй таблицу переходов или диаграмму
  состояний.
- Если важна последовательность участников или систем, используй сценарий или
  sequence diagram.
- Если важно положение системы среди внешних участников, используй
  контекстную диаграмму.
- Если отношения данных неочевидны, используй ERD и словарь данных.
- Если модель не делает смысл яснее, не добавляй диаграмму.

### 6. Проверь специальные области

Открывай только применимые ветки.

**Данные**

- источник и владелец;
- поля, типы, обязательность, формат и значения по умолчанию;
- ключи, уникальность, валидация и нормализация;
- состояния и CRUD;
- транзакционность и конкурентные изменения;
- хранение, архивирование, удаление, чувствительность и аудит.

**Интеграция**

- инициатор и владельцы систем;
- endpoint/topic/file, протокол и версия контракта;
- схема и сопоставление полей;
- аутентификация и авторизация;
- таймаут, retry/backoff, идемпотентность и дубли;
- порядок доставки, частичный успех и коды ошибок;
- совместимость, correlation ID, логи, метрики и алерты.

**Отчет, экспорт или панель**

- источник, срез и момент консистентности данных;
- фильтры, сортировка, агрегаты и округление;
- формат, кодировка, локаль и часовой пояс;
- пустой результат, лимиты и частичные ошибки;
- период обновления, детализация и срок доступности результата.

**Изменение существующего поведения**

- исходное и целевое состояние;
- существующие записи и миграция;
- совместимость и переходный период;
- откат или компенсирующее действие;
- затронутые требования, код, тесты, документация и эксплуатация.

**Атрибут качества**

Формулируй:

```text
При <нагрузка, объем и среда> показатель <метрика> должен быть <граница>,
измеренный <методом> на <интервале>.
```

Если значения нет в источнике, пиши `[требует согласования]`, а не придумывай
правдоподобную цифру.

### 7. Напиши атомарные требования

Используй форму:

```text
[ID] При <событие или условие> система должна <одно наблюдаемое поведение>
<с ожидаемым результатом или измеримым ограничением>.
```

Для каждого требования проверь:

- одна основная обязанность;
- понятное условие применения;
- наблюдаемый результат;
- единые термины;
- активный залог;
- осуществимость;
- проверяемость;
- связь с целью или сценарием.

Не оставляй без расшифровки слова `быстро`, `удобно`, `корректно`,
`надежно`, `безопасно`, `оптимально`, `достаточно`, `поддерживать`,
`обрабатывать`, `при необходимости`, `и так далее`.

Для чисел проверь минимум, максимум, ноль, пустое значение, включенность
границ и пересечения диапазонов. Для коллекций — пустой набор, один элемент,
лимит и превышение. Для повторов — идемпотентность и дубли. Для времени —
часовой пояс, точность, границы интервала и просрочку.

### 8. Сформируй приемку и DoD

Acceptance criteria доказывают поведение продукта:

- основной успешный сценарий;
- существенные альтернативы;
- ошибки и пограничные значения;
- итоговые состояния и побочные эффекты;
- измеримые качества в согласованной среде.

Каждый AC должен подтверждать конкретное требование или цель. Given/When/Then
используй, когда эта форма делает условие и результат яснее; не превращай ее в
ритуал.

Definition of Done доказывает полноту поставки:

- реализация, конфигурация и миграции;
- автоматические и необходимые ручные проверки;
- контракты, документация и наблюдаемость;
- совместимость, переход и откат;
- фактическая проверка результата в нужной среде.

Статус MR, зеленый pipeline, merge и развертывание — разные факты. Не подменяй
один другим.

### 9. Пройди контрольные ворота

Перед выдачей проверь:

1. **Основание:** понятны проблема, пользователь и цель.
2. **Границы:** входят/не входят, зависимости и допущения не конфликтуют.
3. **Поведение:** покрыты успех, альтернативы, ошибки и состояния.
4. **Типы:** правила, данные, интерфейсы, качества и работы не смешаны.
5. **Формулировки:** требования атомарны, однозначны и проверяемы.
6. **Трассировка:** AC подтверждают требования, а требования ведут к цели.
7. **Честность:** придуманных фактов и значений нет.

Исправь редакционные дефекты самостоятельно. Вынеси оставшееся как:

- `блокирующее` — меняет scope, бизнес-правило, необратимое решение или
  приемку;
- `существенное` — допускает разные реализации или проверки;
- `редакционное` — не меняет смысл.

### 10. Реши, нужен ли вопрос пользователю

Если неизвестное существенно меняет scope, бизнес-правило, необратимое
решение или приемку, задай один конкретный вопрос.

Иначе не останавливай работу: подготовь полезный черновик, явно укажи
допущение и открытый вопрос.

Не задавай вопрос, ответ на который можно безопасно получить из доступного
канонического источника.

## Формат результата

Сохраняй проектный шаблон, если он дан. Иначе выбирай минимальный достаточный
масштаб:

```markdown
# <Действие и объект>

## Контекст и цель
## Пользователи
## Входит / не входит
## Сценарии
## Требования
## Acceptance criteria
## Definition of Done
## Допущения
## Открытые вопросы
```

Удаляй неприменимые разделы. Небольшую локальную задачу не раздувай до SRS;
интеграцию, миграцию или рискованное изменение не сжимай до трех строк.

Выдавай в таком порядке:

1. Готовый текст постановки или findings ревью.
2. Допущения, на которых реально держится результат.
3. Только существенные открытые вопросы.
4. Короткий остаточный риск, если он есть.

## Короткий пример преобразования

Вход:

```text
Сделать удобную и быструю выгрузку всех отчетов.
```

Не принимай слова `удобную`, `быструю` и `всех` как готовые требования.
Преобразуй смысл:

```text
BR-1. Пользователь должен получать единый результат по доступным ему отчетам.

FR-1. При запуске выгрузки система должна сформировать отдельный файл для
каждого выбранного отчета и объединить файлы в один архив.

FR-2. Если один отчет сформировать невозможно, система должна завершить
формирование остальных и включить сведения об ошибке в результат.

QR-1. Для <контрольный набор и среда> архив должен быть доступен не позднее
```
