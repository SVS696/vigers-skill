# Шаблоны постановки

## Выбор масштаба

| Масштаб | Когда применять | Обязательное содержание |
|---|---|---|
| Короткий | Локальное изменение с понятным контекстом | Цель, scope, требования, acceptance criteria, DoD |
| Стандартный | Функция, интеграция, отчет, изменение процесса | Полный шаблон ниже |
| Расширенный | Несколько ролей, систем или высокий риск | Стандартный шаблон плюс модели, трассировка и план изменений |

Не раздувай локальную задачу до SRS. Не сжимай интеграцию или рискованное
изменение до трех предложений.

## Короткая постановка

```markdown
# <Действие и объект>

## Контекст и цель
<Какая проблема решается, для кого и какой результат ожидается>

## Входит в задачу
- ...

## Не входит в задачу
- ...

## Требования
- FR-1. При ... система должна ...
- QR-1. При ... показатель ... должен ...

## Acceptance criteria
1. Given ... When ... Then ...
2. Негативный или пограничный сценарий ...

## Definition of Done
- Реализация и необходимые миграции выполнены.
- Автоматические проверки покрывают перечисленные сценарии.
- Наблюдаемость и документация обновлены, если применимо.
- Результат проверен в целевой среде.
```

## Стандартная постановка

```markdown
# <Краткое название: действие + объект + граница>

## Контекст / проблема
<Текущее поведение, боль, источник запроса>

## Бизнес-цель
<Измеримый эффект или наблюдаемый критерий успеха>

## Пользователи и заинтересованные стороны
- <Класс/роль>: <цель и влияние>

## Scope
### Входит
- ...

### Не входит
- ...

## Предусловия и зависимости
- ...

## Целевой сценарий
1. <Триггер и действие пользователя/системы>
2. <Реакция системы>
3. <Результат и состояние данных>

## Альтернативы и ошибки
- <Условие> -> <ожидаемая реакция> -> <состояние после ошибки>

## Функциональные требования
- FR-1. При ... система должна ...
- FR-2. ...

## Бизнес-правила
- RULE-1. ...

## Данные
- DATA-1. <Источник, поля, формат, обязательность, валидация, хранение>

## Внешние интерфейсы
- IR-1. <Контракт, инициатор, таймауты, ошибки, идемпотентность>

## Атрибуты качества
- QR-1. При <нагрузка/среда> <метрика> должна быть <граница>.

## Ограничения и решения
- CON-1. <Согласованное ограничение, источник и причина>

## Acceptance criteria
1. Given ... When ... Then ...
2. ...

## Definition of Done
- Код/конфигурация/миграции выполнены в заявленном scope.
- Проверки подтверждают основной, негативные и пограничные сценарии.
- Контракты, документация и наблюдаемость обновлены.
- Обратная совместимость или план перехода проверены.
- Есть фактическое подтверждение результата; зеленый pipeline сам по себе
  не доказывает публикацию или merge.

## Допущения
- ...

## Открытые вопросы
- <Вопрос> — влияет на <scope/правило/приемку>.
```

Удаляй неприменимые разделы, а не оставляй пустые заголовки.

## Интеграционная добавка

Для интеграции обязательно добавь:

- последовательность вызовов;
- владельцев систем;
- направление и инициатора обмена;
- версии контрактов;
- сопоставление полей;
- таймауты и retry;
- идемпотентность и дубли;
- частичный успех;
- обратную совместимость;
- correlation ID, логи, метрики и алерты.

## Добавка для отчетов и экспорта

Укажи:

- источник и срез данных;
- применяемые фильтры;
- момент консистентности;
- формат, кодировку, локаль и часовой пояс;
- порядок колонок, типы и округление;
- лимиты строк/листов/файлов;
- поведение при пустом результате;
- частичные ошибки;
- имя файла и срок доступности;
- требования к памяти, времени и доставке результата.

## Добавка для изменений данных

Укажи:

- исходное и целевое состояние;
- миграцию и обратную совместимость;
- обработку уже существующих записей;
- конкурентные изменения;
- транзакционные границы;
- аудит;
- откат или компенсирующее действие.

## Acceptance criteria и DoD

Acceptance criteria отвечают: «Как доказать нужное поведение продукта?»

Definition of Done отвечает: «Какие работы и доказательства должны существовать,
чтобы поставку считать завершенной?»

Не включай в acceptance criteria внутреннюю реализацию, если она не является
согласованным ограничением. Не заменяй Acceptance criteria пунктом «задача
протестирована».

## Мини-пример

Вместо:

```text
Сделать удобную и быструю выгрузку всех отчетов.
```

Пиши:

```text
BR-1. Пользователь должен получать единый архив отчетов, доступных ему на
момент запуска операции.

FR-1. При запуске операции система должна сформировать отдельный файл для
каждого выбранного отчета и поместить файлы в один архив.

FR-2. Если один отчет сформировать невозможно, система должна завершить
формирование остальных и включить в архив файл с перечнем ошибок.

QR-1. Для согласованного контрольного набора данных архив должен быть доступен
не позднее чем через 10 минут после запуска операции.
```

Число «10 минут» допустимо только если оно предоставлено источником или явно
помечено как требующее согласования.
