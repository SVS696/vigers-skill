# Контракт границы решения и горизонта

## Цель

Один частный запрос считается наблюдаемым экземпляром потребности, а не
автоматически полным описанием класса задач. Vigers анализирует систему шире
текущего экземпляра, но реализуемый scope расширяет только доказательствами.

Рабочая формула:

> Анализировать системно, реализовать подтверждённый объём и не загнать решение
> в тупик.

Системное понимание не означает немедленную универсализацию реализации.

## Горизонты

### `tactical`

Только для подтверждённого срочного дефекта или ограничения существенного
риска. Решение узкое, обратимое и содержит:

- причину исключения и source refs;
- ограничение текущего решения;
- способ безопасного отката или замены;
- наблюдаемое событие возврата к системному решению.

Выбор требует `architecture_design=pass`.

### `bounded-systemic`

Значение по умолчанию для обычной задачи. Анализ выявляет корневую способность,
инварианты и вариативность; поставка покрывает только подтверждённый текущий
scope и сохраняет дешёвую точку расширения. Если осмысленной точки расширения
нет, это объясняется явно. Сам по себе этот горизонт не включает
архитектурный гейт.

### `generalized-capability`

Допустим, когда подтверждены минимум два варианта либо есть source-linked
roadmap или признак дорогой/необратимой будущей переделки. Реализуется общий
механизм только для подтверждённых вариантов. Выбор требует
`architecture_design=pass`.

## Двусторонний барьер

Ищи два противоположных запаха:

- `particular-case` — клиент, роль, канал, значение или условие захардкожены,
  хотя evidence подтверждает общий класс потребности;
- `speculative-generalization` — абстракция, metadata, rule engine,
  конфигуратор или админский механизм добавлены «на будущее» без подтверждённого
  варианта, roadmap или цены необратимости.

Сначала проверь обоснованную границу, затем запускай `simplicity-spec`. Проход на
простоту удаляет спекулятивный обвес, но не доказанную расширяемость.

## Предварительный probe

Планировщик ищет аналоги в объявленных профилем backlog, коде, процессах и
прошлых постановках. Он сохраняет запросы, отрицательный результат и source
refs в `plan.json.solution_boundary_probe`:

- наблюдаемый кейс и кандидат корневой способности;
- просмотренные поверхности;
- подтверждённые и предполагаемые варианты раздельно;
- roadmap и признаки необратимости;
- кандидат горизонта или `undetermined`;
- подтверждение срочного исключения, если оно есть.

Это гипотеза planning-stage. Полный анализ обязан подтвердить, изменить или
отклонить её; probe не задаёт scope и не подменяет solution decision.

## Финальная запись

Не создавай отдельный runtime-артефакт. Вставь ровно один блок в существующий
`decisions.md`:

<!-- vigers:solution-boundary:start -->
```json
{
  "schema": 1,
  "solution_horizon": "bounded-systemic",
  "observed_case": "Наблюдаемый запрос",
  "root_capability": "Корневая пользовательская способность",
  "invariants": ["Подтверждённый инвариант"],
  "confirmed_variants": [
    {"name": "Текущий вариант", "evidence_refs": ["SRC-001"]}
  ],
  "hypothesized_variants": [],
  "current_scope": ["Что реализуется сейчас"],
  "extension_seams": ["Какая дешёвая точка вариативности сохраняется"],
  "extension_seam_absence_reason": null,
  "deferred_variants": ["Что явно не входит сейчас"],
  "expansion_triggers": ["Какое событие даст основание расширить scope"],
  "horizon_evidence": {
    "analogy_search_refs": ["SRC-001"],
    "roadmap_refs": [],
    "irreversibility_signals": []
  },
  "hotfix_exception": null,
  "planning_probe_disposition": {
    "status": "confirmed",
    "rationale": "Полный анализ подтвердил предварительную границу"
  }
}
```
<!-- vigers:solution-boundary:end -->

`confirmed_variants` всегда имеют evidence. `hypothesized_variants` не входят в
scope. `extension_seams` могут быть пусты только с
`extension_seam_absence_reason`. Для `tactical` обязателен `hotfix_exception` с
`reason`, `source_refs`, `reversibility` и `return_trigger`; для остальных он
равен `null`.

## Гейты и handoff

- Новый planning handoff делает финальную запись обязательной до
  `author_passes`.
- Изменение `decisions.md` или planning-role-context после `author_passes`
  делает гейт stale по subject hash.
- `tactical` и `generalized-capability` требуют `architecture_design=pass` до
  author passes и независимого `architecture_conformance=pass` до финала;
  `bounded-systemic` включает эти гейты только при обычных архитектурных
  triggers.
- Постановка и delivery handoff явно разделяют `current_scope`,
  `extension_seams`, `deferred_variants` и `expansion_triggers`.
- Исполнитель получает принятый горизонт, но не расширяет scope и не
  переизобретает горизонт самостоятельно.
