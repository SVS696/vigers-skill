# Профиль постановок Generic

## Область

Fallback для проекта без специального профиля. Использует ближайшие проектные
инструкции, актуальные источники и минимальный достаточный шаблон Вигерса.

## Канонические источники

1. Явные решения пользователя.
2. Ближайшие `AGENTS.md`, `CLAUDE.md` и другие объявленные проектом доктрины.
3. Актуальный код, API, схема данных, тикеты и документация.
4. Модель требований и метод Вигерса.
5. Старые постановки только как исторический контекст.

## Планирование и внешние артефакты

- Research matrix начинается с явного запроса, ближайших проектных инструкций и
  актуальных tracker/wiki/code sources, если они доступны и применимы.
- Для solution-boundary probe проверь доступные backlog, код, процессы и прошлые
  постановки на аналогичные варианты; сохрани отрицательный результат. Срочный
  tactical fix допустим только по явному источнику срочности или риска.
- Без локального правила ни одна внешняя система не считается обязательной, а
  отрицательный результат поиска фиксируется как coverage gap.
- Passport живёт в локальном planning-case с временным ID, пока проект не
  объявил канонический registry и путь.
- External targets по умолчанию имеют `authority: none`. Создание артефактов в
  личном task manager, tracker или wiki разрешено только явным запросом
  пользователя и с обязательным read-back.
- Видимая рабочая проекция опциональна. Если пользователь или локальные правила
  задают файл, tracker либо wiki как место растущего черновика, объяви target с
  `working_projection: true` и подходящим
  `evidence_kind: local_file|external_readback`, создай или свяжи его после
  approval и до полного анализа. Иначе явно покажи черновик в согласованном
  канале; скрытый runtime case сам по себе не считается доступным пользователю
  результатом.
- Не создавай дублирующий локальный файл, если выбранный target уже является
  tracker description или wiki page/delta. Для project file подтверждай
  read-back через `local_file`; для внешней системы сохраняй JSON receipt
  проектного адаптера и используй `external_readback`.
- `before_research` targets по умолчанию отсутствуют. Их можно объявить только в
  локальном profile как обязательные пустые учётные anchors.
- Объявленный profile task manager отражает личное обязательство и ближайшее
  действие. Checklist title остаётся понятным сам по себе; дополнительные
  details/done_when профиль может поместить в note родительской задачи. Subtask
  создаётся только для самостоятельного результата, dependency или owner.
- До approval запрещены смена workflow status, назначение исполнителя, обещание
  срока и начало реализации.

## Системный анализ

- Отделяй факты от решений, предположений и неизвестного.
- Не присваивай пользователю ответственность бизнес-владельца.
- Описывай проверяемое поведение и ограничения, а не реализацию по догадке.
- Один частный запрос рассматривай как экземпляр возможной общей способности.
  Подтверждённые варианты влияют на границу, предполагаемые — только явно
  откладываются. По умолчанию применяй `bounded-systemic` из общего контракта.

## Архитектурный гейт

Используй общий архитектурный гейт из `SKILL.md`. Дополнительных проектных
триггеров нет.

## Режимы и разбиение

- `compact` — один связный смысловой контур.
- `block` — несколько сценарных/контрактных контуров или большой корпус
  источников; делить по смыслу, не по разделам шаблона.
- Дополнительных `project-trigger` нет; используй общие наблюдаемые признаки из
  `suggest-mode`.
- В block-mode используй 3–8 блоков: контекст/сценарии, правила/состояния,
  данные/интерфейсы, ошибки/качества, AC/DoD — только применимые сочетания.
- Runtime case храни в отдельной локальной области. Если выбран
  `<project-root>/.vigers/cases/`, каталог `cases/` должен игнорироваться git.

## Артефакт и author gates

Если шаблон проекта не найден, используй минимальную структуру:

- контекст и цель;
- пользователи;
- входит / не входит;
- сценарии и требования;
- данные / интерфейсы / качества — только применимое;
- AC;
- DoD;
- допущения и открытые вопросы.

Контрольные проходы:

1. Простота решения.
2. Логика и трассировка.
3. Чистота прозы для фактической аудитории.
4. Независимый reviewer.
5. Architect conformance по общему гейту.

Project-conformance проверяет только затронутые соглашения из ближайших
инструкций: API/HTTP, identifiers/casing, терминологию, frontmatter, шаблон,
ссылки и имена файлов. При отсутствии правил gate помечается `not_required` с
причиной.

## Жизненный цикл и публикация

Не изменяй внешний трекер и не выбирай канонический путь по догадке. При
отсутствии проектного правила выдай готовый текст в чате или согласованном файле.
