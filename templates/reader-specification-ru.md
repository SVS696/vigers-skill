  - [Клиентские состояния: [[#STATE-...|STATE-...]].]
  - [Приёмка поздних ответов: [[#AC-...|AC-...]].]

Не собирайте действия и ссылки в один абзац через запятые и не используйте список `Подробнее: логика работы, требования, критерии приёмки`: оба варианта не объясняют, куда идти конкретному разработчику. Верхний пункт списка описывает действие, вложенные пункты отдельно сопоставляют ему назначение ссылки. Диапазон семантических кодов не записывайте как `SCN-001–SCN-007`: используйте форму `от SCN-001 — «Название» до SCN-007 — «Название»` с отдельной точной ссылкой на каждую границу. Каждый изменяемый компонент должен вести хотя бы к одному точному owner-specific пункту или подразделу; общая сквозная ссылка может быть только дополнительной.

Если затронут другой компонент, добавьте его отдельным H3. Совместный контракт определите один раз в подробном разделе, а из каждого компонентного блока дайте ссылку на него. Если один подробный раздел содержит работу нескольких компонентов, сгруппируйте его содержимое под H3-заголовками `Backend (BE)`, `Frontend (FE)` и при необходимости `Совместно: BE + FE`, а пункты внутри оформите как H4. Жирная строка с названием владельца не заменяет заголовок и запрещена как граница блока. Существующие смысловые подгруппы можно сохранить, добавив владельца в их название. Не чередуйте обязанности BE/FE в одном списке. `Совместно: BE + FE` используйте только для действительно общей обязанности: согласованности контракта и потребителя, порядка поставки, совместного lifecycle или сквозной приёмки; сам факт обмена через API не делает весь раздел совместным.

Описывайте только дельту. Не добавляйте request/response/error примеры, таблицы, коды и отдельные разделы только ради фиксации того, что они не изменяются. При необходимой границе совместимости достаточно одной короткой фразы `Остальной контракт не изменяется.`

Для самостоятельной FE-подзадачи используйте сокращённую reader-структуру: `Кратко о задаче` с `Проблема → Цель → Суть решения` → `Состав изменений` с `Backend (BE): Изменений нет.` и полным `Frontend (FE)` → ссылка на родителя → FE-scope → карта вызовов с конкретными триггерами → состояния и ошибки → зависимости и границы → AC → DoD. Ссылка на родителя не заменяет FE-содержание. Необходимые wire-контракты можно повторить как backend-зависимость без backend scope. Раздел `История изменений` в такой подзадаче удалите.

Таблица допустима для FE-карты вызовов, полезного сравнения одинаковых коротких признаков и маппинга `поле API → источник/назначение → преобразование/условие`; она не заменяет описание, запрос и ответ конкретной операции.
